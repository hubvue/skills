# skills

Claude Code 技能集合，扩展 Claude Code 的前端分析、项目理解和生产力功能。

## 概述

本仓库包含可重用的技能，可通过 `/skill-name` 命令在 Claude Code 中调用。每个技能都是独立的，并通过 Claude Code marketplace 分发。

## 要求

- Node.js >= 20.0.0
- 能够运行 npx bun 命令

## 安装

### 快速安装（推荐）

```shell
npx skills add hubvue/skills
```

### 注册为插件市场
在 Claude Code 中运行以下命令：

```claude
/plugin marketplace add hubvue/skills
```


## 插件

### fe-analysis

前端项目分析工具，用于理解架构、依赖和测试。

#### 技能

- **architecture-analysis** - 综合前端架构分析器，可识别技术栈、构建工具和架构模式。支持检测 Vue/React/Angular 框架、Node.js 环境、包管理器、TypeScript 使用情况、代码检查工具和架构模式。提供多种输出格式，包括 JSON、Markdown、执行摘要和评分卡。

  **何时调用：** 当您需要快速了解项目的结构、依赖关系和技术配置时。

  **命令：**
  ```bash
  cd fe-analysis/architecture-analysis
  npm test                    # 在测试项目上运行
  node scripts/analyze-project.js /path/to/project  # 分析任何项目
  ```

- **dependency-analysis** - 增强的依赖分析器，提供全面的 Markdown 报告和可操作的建议。执行安全扫描、未使用包检测、幽灵依赖识别、循环依赖检测和清理脚本生成。支持 JavaScript、TypeScript、Vue、React、Angular 和现代构建工具，具有并行处理和增量分析功能。

  **何时调用：** 当您需要优化依赖关系、检测漏洞、识别未使用的包、查找重复功能、分析依赖影响、生成清理脚本或生成详细的 Markdown 报告时。

  **命令：**
  ```bash
  cd fe-analysis/dependency-analysis
  npm install                 # 安装依赖（acorn、acorn-walk、semver）
  npm test                    # 在测试项目上运行
  npm run analyze             # 分析当前目录

  # 具有所有功能的完整分析
  node scripts/enhanced-analyzer.js /path/to/project \
    --generateFixScript --generateGraph --checkSecurity --checkOutdated

  # 大型项目的并行处理
  node scripts/enhanced-analyzer.js /path/to/project --parallel --incremental
  ```

- **unit-test-generator** - 面向前端项目的智能单元测试生成器，可检测现有测试框架并为函数、组件和模块生成综合测试。通过分析现有测试模式保持框架一致性。支持 Jest、Vitest、Mocha 以及 React、Vue、Angular 框架。

  **何时调用：** 当您需要（1）向现有代码库添加单元测试，（2）为新项目设置测试基础设施，（3）为特定函数或组件生成测试用例，（4）确保跨项目测试方法的架构一致性时。

  **命令：**
  ```bash
  cd fe-analysis/unit-test-generator
  npm test                    # 检测测试项目中的框架

  # 为特定文件生成测试
  node scripts/generate-test.js src/components/Button.js

  # 为新项目设置测试配置
  node scripts/setup-test-config.js vitest '{"vue": true}'
  ```

### project

与文档和分析相关的项目技能。

#### 技能

- **resume-project-analyzer** - 通过 5 步工作流程将代码库转换为真实、可防御的简历项目经验。分析项目结构、提取工程价值、对信心级别进行分类、进行反思性提问并生成结构化输出。优先考虑正确性和面试可信度，而不是夸大。

  **何时调用：** 当分析代码库以提取适合简历的项目描述、为技术面试问题做准备、理解工程深度或识别可防御的技术成就时。

  **关键工作流程（5 步）：**
  1. 项目分析 - 了解代码库结构、技术栈、架构、复杂性
  2. 工程价值提取 - 识别解决的核心问题、可见的约束、工程决策
  3. 信心分类 - 将每个声明分类为高/中/低（中/低需要用户输入）
  4. 反思性提问 - 在确定简历内容之前提出有针对性的问题
  5. 简历和面试输出 - 使用模板生成结构化输出

  **输出结构：** 固定格式，包括项目摘要、适合简历的项目经验、关键技术亮点、面试防御准备和信心说明。

- **api-generator** - 专精于项目感知 API 集成的自主前端代码生成代理。将后端 API 规范和模拟数据转换为前端请求代码、类型、mock 和测试，严格遵循现有的项目约定。

  **何时调用：** 当用户提供需要前端请求代码的后端 API 规范、要转换为请求类型和处理程序的模拟数据、要添加的 API 端点（带有类型 mock 和测试），或遵循现有项目约定的新 API 集成时。

  **关键工作流程（3 个阶段）：**
  1. 项目侦察 - 检测 TypeScript、请求模式（axios/fetch/umi-request/apollo/react-query/swr/custom）、mock 基础设施（msw/vite-plugin-mock/mockjs/custom）和测试框架
  2. 计划模式 - 在执行之前生成强制性计划，包括项目侦察摘要、功能限制的输出、文件更改列表和增量合并策略
  3. 执行 - 遵循检测到的项目模式生成请求函数、类型、模拟数据和测试

  **安全规则：** 绝不重构不相关的代码，绝不删除现有代码，仅首选添加性更改。

- **prd-gatekeeper** - 工程产品需求文档（PRD）看门人，根据 5 个严格质量门槛验证 PRD，并确保为工程师提供生产就绪的文档。当存在工程风险时阻止进度。

  **何时调用：** 当审查 PRD 以确保其生产就绪且不包含将推送到实现阶段的隐式产品决策时。

- **project-handover-generator** - 从当前代码库和项目工学生成实用的项目交接文档。基于实际仓库证据建立交接内容，帮助继任者了解项目是什么、如何运行、哪些内容未完成/有风险以及需要注意什么。

  **何时调用：** 当准备辞职或交接文档、总结项目架构和职责、为继任者解释部署/配置/风险/待处理工作，或生成结构化的、可编辑的交接文档时。

  **关键工作流程（5 步）：**
  1. 检查仓库 - 了解结构、框架、工具、脚本、配置、文档、部署线索、测试设置
  2. 构建基于证据的理解 - 形成对项目作用和最重要事项的基于证据的心智模型
  3. 识别不确定性 - 区分确认的事实、高置信度推断和未知事项
  4. 生成交接文档 - 生成专为人工接管优化的结构化 markdown 交接文档
  5. 添加最终验证 - 包括需要确认的项目、高风险区域和第一周推荐操作

- **doc-generator** - 基于源代码生成、更新或改进项目、文件、组件、SDK、模块或函数的使用文档。支持项目级别（整个仓库）、文件级别（单个文件/模块）和符号级别（函数/类/组件）目标。生成使用导向的文档，包括何时/如何使用、约束和常见陷阱。

  **何时调用：** 当需要为项目、文件、组件、SDK、模块或函数生成、更新或改进基于源代码的使用文档时。

  **关键工作流程（5 步）：**
  1. 确定文档目标和范围
  2. 检查相关代码和项目上下文
  3. 从源码推断使用方式、约束和集成点
  4. 生成结构化的 Markdown 使用文档
  5. 在证据不足时明确说明假设、缺口和验证点

- **project-migration** - 规划并推进安全的旧仓库到新仓库项目迁移，提供分阶段输出、风险控制和迁移工件。帮助团队审计接手项目、比较新旧仓库、定义迁移批次、选择试点业务切片、管理兼容层，以及验证发布与回滚准备情况。

  **何时调用：** 当需要将现有项目迁移到新仓库、技术栈或工程体系，尤其是需要审计结果、差异矩阵、迁移计划、试点范围、执行日志或验证清单时。

  **关键工作流程：** 按阶段推进迁移：
  1. Intake - 明确范围、约束、成功标准和迁移策略
  2. Audit 和 Map - 了解旧项目、核心流程、隐式依赖和样式资产
  3. Diff 和 Plan - 比较新旧仓库，设计适配层，定义批次和试点范围
  4. Execute 和 Verify - 跟踪迁移进度、阻塞项、验证、发布准备和回滚
  5. Cleanup - 清理迁移债务并定义后续治理

- **breaking-refactor** - 规划、执行并验证有意为之的破坏性重构：在不保留运行时向后兼容的前提下替换既有设计。协调范围内消费方同步更新，移除兼容层与双路径，并产出影响分析、切换计划，以及旧设计已清除的证据。

  **何时调用：** 当用户明确授权在可控范围内做不兼容变更——替换 API、模块、架构、数据模型、schema、事件、配置或 CLI 契约——且范围内所有消费方可以在一次协同变更中更新时。

  **关键工作流程：** 确立重构契约 → 分析影响与破坏面 → 规划切换与验证 → 落地单一规范设计 → 确认旧路径已清除且必须保留的行为仍然正确。

- **clean-code** - Clean Code 规范总览与路由，覆盖命名、函数、注释、格式、对象与数据结构、错误处理、边界、测试、类、系统、并发、简单设计、渐进式重构及各类代码坏味道。按需加载 references 中对应的规则文件，而非一次性加载全部规则。

  **何时调用：** 当进行代码审查、重构、编写新代码，或询问 Clean Code / 整洁代码 / 代码坏味道 / 可读性相关问题时。

  **关键行为：** 充当主题路由——识别相关的整洁代码关注点，并加载对应的参考规则文件（如有意义的命名、函数、错误处理、代码坏味道），以应用聚焦的指导。

### context-engineering

用于提示优化和管理的上下文工程技能。

#### 技能

- **prompt-minifier** - 在保持行为语义等价的前提下，将冗长的提示词压缩为精简的最小提示词。将冗长或冗余的提示词转换为最小化、高密度的提示词，同时保持等效的语义和行为约束。

  **何时调用：** 当用户想要（1）压缩冗长的提示词以提高 token 效率，（2）在保持等效语义的同时优化提示词结构，（3）从现有提示词中删除冗余，（4）将自然语言提示词转换为紧凑的结构化格式时。

  **关键原则：**
  - 保留语义意图和约束
  - 删除冗余、填充词和隐式默认值
  - 尽可能将自然语言压缩为结构化指令
  - 最大化每个 token 的信息密度
  - 避免更改任务范围或含义

  **压缩级别：** 无损（保留完整的显式含义）、平衡（删除冗余，保持清晰）、激进（最大 token 减少）。

- **prompt-interviewer** - 高级提示工程师和提示面试官，通过结构化分析和迭代式提问来帮助用户完善和完成提示。作为面试官而不是提示重写器，确保提示在执行前明确且结构良好。

  **何时调用：** 当用户有一个初始提示但需要帮助改进它以获得更好的 LLM 性能时：（1）当提示缺乏清晰度或上下文时，（2）当缺少约束或边界时，（3）当未定义输出格式或质量标准时，（4）当存在歧义或冲突要求时。

  **关键工作流程（6 步）：**
  1. 提示分析 - 分析目标清晰度、上下文完整性、约束、受众、I/O 格式、质量标准、边缘情况
  2. 面试模式 - 针对缺失的信息提出具体、高影响力的问题（绝不假设或默默填补空白）
  3. 迭代循环 - 在每次回答后重新分析，继续面试直到完成
  4. 完成标准 - 仅在目标、角色、输入、输出、约束都明确时确定
  5. 运行门 - 展示最终提示并询问"您想让我现在使用当前的 LLM 运行此提示吗？"
  6. 最终输出 - 如果用户说"运行"，立即使用当前的 LLM 执行提示

  **关键原则：** 该技能是面试官，而不是提示重写器。问题必须具体、可操作、按主题分组，并解释每个问题为什么重要。

- **context-probe** - 隐式系统级技能，监控上下文完整性、系统提示保留情况和指令漂移。始终隐式运行，无需用户调用。当上下文降级或丢失时发出警告。

  **何时调用：** 永不直接调用 - 此技能在系统级别隐式运行。

  **关键功能：**
  - 检测系统指令、CLAUDE.md 规则和关键上下文是否仍然存在
  - 为外部工具提供机器可读的遥测数据
  - 当上下文降级或丢失时警告用户
  - 自愈行为：在上下文降级时重新陈述关键约束

- **code-evolver** - 从持续对话中沉淀可长期复用的项目规则：代码规范、工程约定、架构约束、命名与目录结构、测试与提交流程、协作方式及 AI 协作规则。识别可复用规则，处理新增/更新/合并/冲突，过滤一次性指令，并按职责将带 few-shot 的规则同步到 `.cursor/rules`、`AGENTS.md` 与 `CLAUDE.md`。

  **何时调用：** 当用户要求把约定写入规则文件、在对话中更新团队规范，或反复出现值得固化为规则的稳定约束时。

  **关键工作流程：** 识别规则候选 → 区分长期规则与临时指令 → 与已有规则做差异对比 → 处理合并与冲突 → 按各载体职责写入或更新文件，并为每条规则补充可判别的 few-shot。

### productivity

用于工作流程优化的生产力工具。

#### 技能

- **skills-workflow** - 交互式技能工作流，用于将多个技能串联，使步骤 i 的输出成为步骤 i-1 的输入。支持 dry-run 模式、跟踪日志、输出验证和安全防护。能够以确定性和可审计性执行复杂的多步骤工作流程。

  **何时调用：** 当您需要（1）按特定顺序串联多个技能，（2）在技能之间传递输出作为输入，（3）执行具有可追溯性的复杂多步骤工作流程，（4）在执行之前以 dry-run 模式运行技能，（5）调试或审核多技能工作流程时。

  **关键工作流程：**
  1. 交互式设置 - 收集管道配置（技能、步骤目标、模板、上下文、执行模式）
  2. 计划输出 - 生成管道计划，显示所有步骤和配置
  3. 执行 - 按顺序运行技能，具有输入/输出串联和验证
  4. 跟踪日志 - 可选的详细日志记录每个步骤的输入、输出和验证结果

  **安全功能：** 当技能不可用时的模拟模式、提示注入保护、日志中的密钥脱敏、未经用户批准不执行破坏性操作。

- **release-skills** - 自动化 kim-skills 插件的发布流程：分析自上次标签以来的更改、更新 CHANGELOG（中英文）、更新 marketplace.json 版本、提交并创建版本标签。

  **何时调用：** 当用户请求发布、发布新版本、版本更新或将未提交的更改推送到远程时。

  **关键工作流程：**
  1. 分析自上次标签以来的更改
  2. 确定版本更新（补丁/次要/主要）
  3. 检查并在需要时更新 README
  4. 更新 CHANGELOG.md 和 CHANGELOG.zh.md
  5. 更新 marketplace.json 版本
  6. 提交所有更改
  7. 创建版本标签

- **skills-workflow-builder** - 通过嵌入固定管道（技能顺序 + 每步目标/模板/合同/停止条件）创建新的专用工作流技能。在运行时只要求 `initial_prompt`（必需），并可选择允许安全覆盖（execution_mode、verbosity、context_append）。

  **何时调用：** 当您想要创建可重复使用的工作流技能而不需要每次都重新输入技能顺序/模板时。

  **关键工作流程：**
  1. 收集管道配置（new_skill_name、new_skill_description、技能顺序、可选的 baked_in_shared_context、默认值、override_policy）
  2. 以 DRY_RUN 模式调用 skills-workflow 以规范化管道配置
  3. 为 NEW_WORKFLOW_SKILL 生成完整的、可复制粘贴的技能定义
  4. 使用 skill-creator 创建技能

- **deep-learning** - 系统化学习和解释库、框架、模块、函数或代码路径的原理。帮助用户构建正确的思维模型，提供从问题和角色到设计权衡和下一步阅读的分层解释。支持项目、模块和函数三种模式，提供全面的工作流指导。

  **何时调用：** 当用户想要理解整体架构、模块职责、执行流程、调用链、核心数据结构、设计权衡、实现细节，或从源代码中获得适合面试的解释时。

  **核心模式：**
  - 项目模式 - 适用于整个框架/项目
  - 模块模式 - 适用于包/子系统/目录
  - 函数模式 - 适用于函数/方法/钩子/类或窄调用路径

  **关键工作流程：**
  1. 确定目标和范围
  2. 选择合适的模式
  3. 分层解释（问题、结构、主要流程、实现细节、权衡）
  4. 基于提供的代码/上下文进行解释
  5. 以总结和下一步阅读结束

- **dev-spec** - 按任务编排 spec 驱动的 AI 代理开发，包含明确的阶段、每个任务的工件、依赖修复和迭代需求的增量更新。将工作组织为按任务的、阶段门控的工作流程，而不是非结构化聊天。

  **何时调用：** 当您需要用明确的阶段（intake、research、plan、todo、implement、review）、工件优先的输出、从后续阶段开始的依赖修复以及现有工件的增量更新来构建 AI 辅助开发工作时。

  **核心原则：**
  - 任务隔离 - 工作按任务组织，保持不相关需求分离
  - 工件优先 - 每个阶段必须创建或更新持久化工件
  - 更新而非覆盖 - 增量更新现有工件而不是覆盖
  - 依赖修复 - 当用户从后续阶段开始时，自动生成最小的上游工件
  - 审查门控执行 - 优先在广泛实现之前进行研究，在研究之前进行计划
  - 无静默范围扩展 - 保持在当前任务范围内，将相邻工作记录为注释/风险

  **支持的阶段：** intake（需求收集）、research（研究）、plan（计划）、todo（任务清单）、implement（实现）、test（测试）、bugfix（修复）、review（审查）

  **关键工作流程：**
  1. 解释用户输入 - 确定任务识别、请求阶段、模式（创建/更新）和依赖修复需求
  2. 执行请求的阶段 - 遵循参考文档中的阶段特定规则
  3. 输出工作流程摘要 - 包括任务信息、请求阶段、依赖修复、创建/更新的工件和下一个推荐阶段

- **doc-skill-creator** - 将现有文档转换为专用技能设计，包括分析适用性、提取能力、设计技能结构和起草 SKILL.md 及参考资料。将组件库文档、SDK 文档、工具文档、FAQ、迁移指南、标准文档和示例等静态文档转换为实用的技能工件。

  **何时调用：** 当需要将文档转换为专用技能、从库、SDK、FAQ、迁移或标准文档生成技能、从现有文档设计目标技能、从源文档创建 SKILL.md 和参考资料，或将静态文档转换为实用使用能力时。

  **默认工作流程：**
  1. 分析源材料和范围
  2. 判断技能转换的适用性
  3. 确定目标技能类型
  4. 提取能力单元
  5. 在适用时将知识分为事实、规则、场景、示例、陷阱、迁移和缺口
  6. 设计目标技能结构
  7. 起草目标 SKILL.md 和参考资料计划

  **工作规则：**
  - 将文档转换为能力，而不仅仅是摘要
  - 围绕用户任务组织输出，而不是源标题
  - 优先考虑实用指导而非被动描述
  - 清晰地区分已记录的事实和衍生指导
  - 不要发明不受支持的 API、功能或保证
  - 当源材料不完整时，明确说明缺失信息
  - 保持目标技能范围可控且可维护

- **tech-writing** - 将复杂工程项目、框架、工具与实践转化为以读者为中心的中英文技术文章。支持仓库调研、文章定位、章节规划、迭代共写、设计讲解、证据支撑示例、视觉规划、事实核验，以及对 README 风格、空洞、难读或 AI 味过重内容的改写。

### idea-incubation

一个证据驱动的想法孵化工作流，将原始产品想法逐步转化为经过验证、可做决策的完整需求。它只暴露一个公共 Skill，12 个阶段均作为内部 references，由一个命令统一负责路由、状态、证据、修订与持久化产物。

#### 技能

- **idea-incubation** - 执行指定孵化阶段，自动补齐缺失的前置阶段，并在上游阶段被修订时重流受影响的下游产物。

  **CLI 示例：**

  ```bash
  /idea-incubation intake "一个把会议记录转化为产品决策的 AI 助手"
  /idea-incubation motivation
  /idea-incubation feasibility
  /idea-incubation users "首个版本聚焦产品经理"
  /idea-incubation assemble
  ```

  命令格式始终为 `/idea-incubation <phase> [阶段输入]`，不再使用 `start`、`run`、`continue` 等动作子命令。

  **内部阶段：** intake → motivation → users → scenarios → painpoints → value → feasibility → goals → solution → scope → acceptance → assemble。

  每个阶段必须通过输入与输出质量门禁。当缺少影响决策的用户上下文时，工作流每轮只提出一个问题，持久化回答并重新评估门禁；同一阶段可以进行多轮单问题补充。工作流还会区分事实、推断与假设，维护共享来源注册表，并允许暂停、恢复、重流、延后或否决想法，而不是强制生成需求。

```
/<skill-name>/

├── package.json       # Node 依赖（可选）
├── scripts/           # 可执行 Node.js 脚本（可选）
└── references/        # 支持文档（可选）
```
